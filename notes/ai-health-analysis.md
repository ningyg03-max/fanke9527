## 二、数据盘点（逐项核对存储结构）

| 数据 | 有无 | 来源 |
|---|---|---|
| 每日总饮水量 | ✅ | `water_history`，保留 365 天 |
| 饮品类型分布 | ✅ | 同上，按类型聚合（毫升 + 杯数）|
| 热量 | ✅ | `DrinkTypes.kcal()` × 毫升 |
| 含糖杯数 | ✅ | `DrinkTypes.isSugary()` |
| 达标天数 | ✅ | 对比 `WaterReminderSettings.targetMl` |
| **今日时段分布** | ⚠️ | **仅今天**（`water_records` 有毫秒时间戳）|
| 体重/身高/活动量 | ❌ | 完全没有 |

### 盲区 1：历史记录按天聚合，没有时间

```
water_history 格式：
  "20261010:1:3300:8;20261009:0:1500:5;..."
   日期    饮品 毫升 杯数
```

- 只有**今天**的 `water_records` 存逐条毫秒时间戳
- **后果**：无法分析「晚上是不是总缺水」「提醒有没有用」等时段问题（历史追溯不了）
- **要补**：归档时增加时段分桶（如 6 小时一桶）→ 从改动日起积累，旧数据补不回
- **代价**：约 50 行 + 一次格式迁移

### 盲区 2：没有个人资料（体重等）

- AI 无法算个性化目标量（需体重 × 30~35ml 公式）
- **替代方案**：用**相对指标**分析 —— 达标率、白开水占比、含糖比、趋势
  （不需要体重，行动指导性反而更强）

## 三、三条实现路径

### 路径 A：App 内直连 AI API

```
点击 → 组装数据 → HTTPS 调 DeepSeek API → 显示分析
```

| 项 | 评估 |
|---|---|
| 技术 | ✅ 复用现有 `HttpURLConnection` |
| 前置 | ❗ 需用户填 API key |
| 成本 | 约 ¥0.002/次（800 token），可忽略 |
| 工作量 | ~500 行（客户端 + key 输入 + 结果展示 + 错误处理）|
| 风险 | key 本地存储 / **健康数据发往第三方**（须明示）/ 网络失败处理 |

### 路径 B：导出摘要 → 粘贴分析 ⭐ 推荐

```
点击 → 生成结构化摘要 → 复制到剪贴板 → 用户粘贴到 Minis 分析
```

| 项 | 评估 |
|---|---|
| 前置 | **无**（不填 key、不联网）|
| 成本 | 零 |
| 工作量 | **~150 行**（拼文本 + 剪贴板），最小改动 |
| 隐私 | 无第三方 API 风险 |
| 质量 | 反而更高（对话模型上下文更大，可追问）|

### 路径 C：纯本地规则引擎

- 达标率不足 → 提示；含糖高 → 提示
- 缺点：**这不是 AI** —— 死板、读不懂异常模式
- 不推荐独立做

---

## 四、推荐理由（B 优先）

1. **B 是唯一零前置条件的** —— 没有 key 也能用，当天可用
2. **B 分析质量更高** —— 对话模型（1M 上下文）能读懂「啤酒每周 1 次」这类模式，还能追问
3. **B 用来验证「分析有没有用」** —— 觉得一般就不投入 A 的 500 行
4. **A 的真正价值在离线场景**，不是分析质量

## 六、分析输出示例（基于用户真实截图数据）

> 数据：5,350ml / 达标 1 天 / 424 kcal / 含糖 1/12 杯 / 精酿啤酒 500ml

| 维度 | AI 能给出的分析 |
|---|---|
| 充足度 | 7 天总量 5,350ml，日均 **764ml** = 目标的 25%，明显不足 |
| 结构 | 白开水 62%（健康）；运动饮料 + 啤酒占 19% |
| 热量 | 424 kcal/周（≈60 kcal/天），主要来自啤酒和运动饮料 |
| 糖 | 含糖 1/12 杯 —— 控制良好 |
| 酒精 | 精酿 500ml —— 酒精利尿，**抵消补水效果** |
| 建议 | 3~5 条可执行项（如「拆成 6 次 × 500ml」）|
