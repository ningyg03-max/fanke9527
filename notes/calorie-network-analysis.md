# 热量方案可行性分析（实测版）

日期：2026-10-09 · 状态：**仅分析，未实现**
方法：本次不是纸面推理 —— 在沙箱里**真跑了 API 测试**（沙箱运行在手机本体上，走的就是本机网络）

---

## 结论速览

| 方案 | 架构可行性 | 数据可得性 | 推荐度 |
|---|---|---|---|
| A. 输入名称 → 联网查询 | ✅ 可做 | ❌ **数据源不可靠** | ⭐ |
| B. 内置基础数据 + 本地查询 | ✅ **架构最优** | ❌ **免费源拿不到国内数据** | ⭐⭐ |
| C. B + 精选表（人工整理起步） | ✅ | ⚠️ 需人工整理 | ⭐⭐⭐⭐ |
| D. 含糖标记（轻量替代） | ✅ | ✅ 无需外部数据 | ⭐⭐⭐⭐ |

**核心矛盾**：你的架构思路（B）是对的 —— 离线、快、不需要网络权限。
卡点在**数据从哪来**：国内饮料热量数据没有可用的免费开放源。

## 一、实测记录：联网查询（方案 A）

### 测试 1：Open Food Facts 旧接口（cgi/search.pl）

| 关键词 | 结果 |
|---|---|
| 可乐 | 11 条，"可口可乐" 100g=180 kcal ❌（真实值 43）|
| 奶茶 | 3 条，7-11 奶茶 100g=20 |
| **拿铁** | ❌ **503 服务不可用** |
| 牛奶 | 15 条，其中"牛奶泡芙" 584 kcal ❌（搜出的是零食）|
| **橙汁** | ❌ **503** |
| **元气森林** | ❌ **503** |
| 红牛 | 1 条，55.6 |
| **雪碧** | **0 条**（国内常见品牌完全缺失）|

**成功率测试**（连续 6 次同一查询）：**失败 5/6**，全部 HTTP 503
→ 间隔 20 秒重试 4 次：成功 2/4，成功时耗时 **7.0s**

### 测试 2：OFF 新搜索后端（search-a-licious）

响应快（**0.8~1.4s**），成功率 4/4 ✅ —— 但**数据质量不行**：

| 查询 | 返回 |
|---|---|
| 拿铁 | 「生椰拿铁·椰蓉咖啡米面包」219 kcal、「吞拿魚三文治」276 kcal ❌ **全是面包三明治** |
| 牛奶 | 「牛奶」100g=12.5 kcal ❌（真实 60~70）|
| 可乐 | 51 条，但热量字段多为 `None` |

### 测试 3：OFF 的"中国商品"存量

| 查询 | 命中 |
|---|---:|
| `countries_tags:"en:china"` | **1,303 条** |
| 其中 `categories_tags:"en:beverages"` | **149 条** |

抽样 20 条中国饮料，**有热量数据的只有 2 条（10%）**：

```
康师傅鲜果橙       kcal=None
健力宝            kcal=None
百事可乐          kcal=None
康师傅冰红茶       kcal=None
可口可乐          kcal=None
东方树叶茉莉花茶    kcal=0    ← 有数据
劲爽无糖百事可乐    kcal=0    ← 有数据
娃哈哈 AD钙奶      kcal=None
凉白开            kcal=None
```

**商品名是对的，热量字段基本空着。**

### 测试 4：国内数据源（薄荷健康）

API 端点可达（0.3s），但 **搜索接口返回的条目与查询词完全无关**：

| 搜索词 | 返回的"结果" |
|---|---|
| 可乐 | 蜜絮、酸卯竹、筠韭尖、尖鼻葱 |
| 可口可乐汽水 | 蜜絮、酸卯竹、筠韭尖 ❌ **同一批** |
| 农夫山泉饮用水 | 牛油草、花川蓟、菽油果 |
| 伊利纯牛奶 | 菁楠、蚂乷、萝根 |
| 营养快线 | 竹筎根、苦断肠、比日鱼 |

**同一批随机条目反复出现在不同查询里** —— 这个接口是坏的（或需要 App 内签名鉴权）。
虽然偶有真实数据漏出（`无糖可乐=1`、`乌龙奶茶(去冰,微糖)=59`），但**整体不可用**。

## 二、实测记录：内置基础数据（你的方案 B）

### 卡点 1：全量导出太大，无法打包

| 文件 | 大小 |
|---|---:|
| OFF 全量 JSONL（压缩） | **12,502 MB** |
| OFF CSV 导出（压缩） | **1,216 MB** |

APK 目前 **66KB**。即使只抽取饮料类，全量下载在手机端也不现实（且沙箱里跑要很久）。

### 卡点 2：抽取后的可用数据量太少

按测试 3 的结果：中国饮料 149 条 × 有热量 10% ≈ **15 条可用**。
**15 条基础数据撑不起"输入名称查询"这个功能。**

### 卡点 3：GitHub 没有现成的中文食品热量数据集

搜索 `food calorie dataset chinese` → 0 个结果
搜索 `food nutrition dataset china` → 2 个结果，均为学术用途、不含市售饮料

## 三、结论：架构对，数据难

```
你的方案 B 架构：                    ✅ 完全正确
  ├─ 离线基础数据（免网络权限）        ✅ 好
  ├─ 添加饮品时本地查询               ✅ 好
  └─ 数据来源                        ❌ 卡在这里
```

**免费开放数据里没有可靠的国内饮料热量表。** 三条实测路径全部受阻：
- OFF：数据质量差 + 中国库存少 + 热量字段缺失
- 薄荷：接口不可用
- GitHub：无现成数据集

## 四、可行路径（按推荐度）

### ⭐⭐⭐⭐ 路径 1：精选起步表 + 用户可编辑（推荐）

不追求"全"，追求"准"和"能改"：

1. **内置一个精挑的起步表**（30~60 条），只包含：
   - 最常见品类（白开水/茶/咖啡/可乐/牛奶/果汁…）
   - 每个品类给一个**保守中值**
2. **每条都能在设置里改**（和容量、名称一样）
3. **自定义饮品添加时可选填热量**
4. 界面上标「约」

> 关键洞察：既然**每样饮品的名称现在都能改了**（本版已实现），
> 那么"把咖啡改名成美式咖啡 + 改成 2 kcal"这个动作，成本已经很低 —— 
> 相当于用户自己维护自己的热量表。

### ⭐⭐⭐⭐ 路径 2：含糖标记（最轻量）

不做热量，只标「无糖 / 有糖」，统计「今日含糖 N 杯」。

- ✅ 不需要任何外部数据
- ✅ 信息量比假精确的热量数字更实用
- ✅ 改动最小（一个布尔字段 + 一处统计）

### ⭐⭐⭐ 路径 3：本地起步表 + 可选联网补充

基础表离线；查不到时，把名称丢给 OFF 搜一下作为**候选**，用户确认后**存本地**。

- ⚠️ 需要加 `INTERNET` 权限（破坏现在的纯离线特性）
- ⚠️ 命中率低（见测试 3）

### ⭐ 路径 4：纯联网查询（你最初的设想）

- ❌ 成功率 25%~50%，耗时 1~15 秒
- ❌ 中文数据质量差（拿铁搜出面包）
- ❌ 必须加 `INTERNET` 权限
- **不建议**

## 六、一句话总结

**你的思路（内置基础数据 + 本地查询）是对的方向，但"下载市面饮料热量"这一步在免费数据源上走不通** —— 
不是技术问题，是数据问题。建议走「**精选起步表 + 全字段可编辑**」：
起步表不用大，够用就行；**用户能自己改，比数据全更重要**（改名的能力本版已经做了）。
